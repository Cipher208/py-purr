**Окружение:** Windows, Python из `.venv` PURR, SQLite WAL

## Что проверялось

**Сценарий 1 — подтверждённая одиночная запись.**
Дочерний процесс пишет ключи в цикле. Ключ считается подтверждённым только после того, как `set()` вернул `True` **и** подтверждение ушло в stdout с `flush`. Родитель убивает процесс (`kill` → `TerminateProcess` на Windows) после случайных 40-160 подтверждений, затем отдельный процесс открывает базу заново и сверяет.

**Сценарий 2 — атомарность транзакции.**
Процесс пишет 20 подтверждённых ключей, затем внутри `store.transaction()` делает 500 записей, отмечая каждые 50. Родитель убивает его ровно после отметки 100 — то есть гарантированно внутри открытой транзакции. Проверка: либо все 500 видны, либо ни одной; «половина» — частичный коммит, брак.

## Контроль качества самого стенда

Стенд, который всегда говорит «всё хорошо», бесполезен. Проверил, что детектор не слепой:

```
контроль 1: все 5 ключей на месте
  {"confirmed": 5, "survived": 5, "missing": [], "integrity": "ok"}   exit=0

контроль 2: удалил ключ k3 вручную
  {"confirmed": 5, "survived": 4, "missing": ["k3"], "integrity": "ok"}   exit=1
```

Первая версия сценария 2 давала `tx=500/500` во всех прогонах — потому что убийство приходило уже после коммита. Это был брак стенда, а не результат: он «доказывал» то, чего не проверял. Переделал на убийство по отметке `PROGRESS 100` — только тогда тест стал настоящим.

**Сценарий 3 — журнал событий в отдельном файле.**
`Store` с `journal=EventStream(events.db)`: каждая запись в KV должна оставить событие `{"op":"set","key":...}` в другом файле. Проверяется в обе стороны: запись есть — события нет (**разрыв**), событие есть — записи нет (**фантом**). Фантом хуже: replay применил бы мутацию, которой не было.

```
12 прогонов без вмешательства:
  потеряно подтверждённых 0 | разрывов 3 из 12 (в каждом ровно 1) | фантомов 0

run 2: в KV 89  | событий 88  | разрыв 1 (j89)
run 5: в KV 102 | событий 101 | разрыв 1 (j102)
run 6: в KV 127 | событий 126 | разрыв 1 (j127)
```

Разрыв всегда один и всегда последний ключ: убийство попадает в зазор между коммитом KV и записью события. Чтобы проверить сам механизм, а не удачу, расширил зазор — `journal.append` тормозит на 50 мс:

```
4 прогона с расширенным окном: разрыв в 4 из 4 (ровно 1 каждый)
```

Это подтверждает заявленную в отчёте неатомарность: окно существует и воспроизводится. При этом **фантомов нет ни разу** — журнал не обгоняет коммит.

**Сценарий 4 — транзакция + журнал: убийство во время сброса буфера.**
События внутри транзакции копятся в буфере и пишутся после коммита. Маркер ставится на первом `append` — значит KV уже закоммичен, а журнал ещё нет. Убийство приходит в этот момент.

```
run 1: маркер=да | tx в KV 500/500 | событий tx 3   | разрыв 497 | integrity ok
run 2: маркер=да | tx в KV 500/500 | событий tx 3   | разрыв 497 | integrity ok
run 3: маркер=да | tx в KV 500/500 | событий tx 3   | разрыв 497 | integrity ok
```

**Разрыв здесь не один, а почти вся пачка.** Транзакция закоммичена целиком, а журнал успел записать 3 события из 500. Причина: `JournalFlushError` честно сообщает о *сбое* записи, но аварийное убийство не бросает исключение — процесс просто исчезает, и сообщать некому.

## Что это доказывает

На этой машине, при этой версии SQLite и WAL:

1. Запись, подтверждённая вызывающему (`set()` вернул `True`), переживает аварийное убийство процесса. 954 из 954.
2. Открытая транзакция при убийстве не оставляет частичных данных: 0 из 500 в шести прогонах. Атомарность держится.
3. Файл базы после аварии открывается, `PRAGMA integrity_check` чистый.
4. **Журнал может отстать от KV.** На одиночных записях — ровно на одно событие (3 из 12 прогонов, 4 из 4 при расширенном окне). На транзакции — почти на всю пачку: 497 из 500 в трёх прогонах из трёх. Фантомных событий (журнал впереди базы) не было ни разу.

## Чего это НЕ доказывает

- **Размер разрыва ограничен только размером пачки.** Проверено на 500 записях в транзакции — потеряно 497. На пачке в 50 000 будет так же. Механизма восстановления потерянных событий нет: после рестарта ничто не сигналит о дыре.
- **Журнал событий (`EventStream`) не проверялся.** Он живёт в отдельном файле, и в отчёте аудита прямо записано, что атомарность с KV не гарантируется по дизайну. Стенд этот разрыв не трогал.
- **Мультипроцессная конкуренция** под длительной нагрузкой — не проверялась. Здесь один писатель.
- **Только Windows.** Linux-поведение WAL при kill не проверено, а прод на VPS — Linux.
- **Долгая нагрузка.** Прогоны короткие (секунды). Накопление WAL, checkpoint при живых соединениях, рост файла — вне охвата.
- **Диск.** Имитации сбоя диска нет: убивается процесс, не носитель.

## Что с этим делать (дописано 2026-10-29)

Результат не «всё хорошо» и не «всё плохо». Он делится на два вопроса, и у них разный статус.

**1. Подтверждённая запись переживает крах — закрыто.** 954 из 954, транзакция не оставляет половины (0 из 500 в шести прогонах), база открывается, `integrity_check` чистый. На этой машине это доказано, спорить не о чем.

**2. Журнал событий отстаёт от KV — открытый контракт, а не баг.** Разрыв воспроизводится, фантомов нет, размер разрыва ограничен только размером пачки (497 из 500 на транзакции). Пока контракт не выбран, поведение при крахе не определено: сейчас система молчит, и это худший из вариантов. Три варианта, решение не принято:

- **best-effort.** Журнал явно объявляется необязательным. После рестарта сверяется расхождение и пишется маркер с числом потерянных событий. Дешево и честно; данные не восстанавливаются, но потеря перестаёт быть молчаливой.
- **намерение до коммита.** Перед коммитом KV пишется отметка о намерении, после — отметка о завершении. Незакрытое намерение после рестарта означает возможную дыру, и это видно. Дороже: лишняя запись на транзакцию и другой порядок записи.
- **один файл.** Журнал переезжает в ту же базу и в ту же транзакцию. Атомарность полная, но теряется то, ради чего журнал вынесли в отдельный файл.

**Что должно доказать исправление** (кандидат в критерий приёмки): `run-journal-txn 3` больше не должен показывать молчаливый разрыв — либо `разрыв 0`, либо явный маркер потери, который видно после рестарта. Проверять только этим стендом: юнит-тест аварийное убийство не воспроизводит.
