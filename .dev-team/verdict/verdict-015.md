# Вердикт приёмки № 015

Дата: 2026-10-31
Задача: переводы строк в рабочем дереве не расходятся с git, расхождение ловится тестом
Теги: accept-base = accept-fix = 6b5aed4 (нормализация не создаёт коммита), accept-docs b56aaa5
Приёмщик: Warder (acceptance, режим plan, клоны вне рабочего каталога)
Заход: второй, после отказа по гейту F

## Тело вердикта (транскрипция)

ВЕРДИКТ: ПРИНЯТО

ОСНОВАНИЕ: Дерево в LF (0 CRLF на 100 отслеживаемых файлах, включая `.dev-team/`), тест не вакуумный (ловит и внедрённый CRLF, и повтор ошибки через `write_text`), CI зелёный, продукт не тронут, гейт E закрыт с двумя отрицательными контролями.

ПРОВЕРЕНО (13 пунктов, ключевые):
- байтовая перепись 100 файлов: 0 CRLF; `git ls-files --eol` → 0 строк `w/crlf`;
- карточная команда ×3 → `5 passed`, `exit=0`; `git status` до и после пуст;
- вакуумность: внедрённый `crlf_probe.py` → `exit=1` с именем и числом строк; снятие → `exit=0`;
- `.png` с CRLF и untracked `.py` не ловятся; `.gitattributes`/`.gitignore`/`LICENSE` в CRLF (следствие `autocrlf=true`) не ловятся — тест молчит по делу, а не потому что нечего ловить;
- **повтор ошибки лида воспроизведён и поймал:** `Path.write_text` на `card.md` → 35 CRLF → `exit=1` с именем файла;
- подмена теста на `assert True` при живом CRLF-дефекте → `1 passed`, гейт её отбрасывает;
- CI: `ruff check` 0, `ruff format --check` 0 (`37 files already formatted`), `pytest -q` 207 passed;
- продукт: `git diff --name-only accept-base~1..accept-docs -- purr tools` пуст;
- бюджет: артефакт `dc9d271..accept-base` = 196 строк ≤ 220;
- гейт E `exit=0`, два отрицательных контроля `exit=1`;
- `ATTEMPT` для gate F = 1; 5 строк `ПРАВКА`, у всех есть ответ.

ЧЕГО НЕ ПРОВЕРЯЛ:
- Классический откат `checkout accept-base → красный` невозможен: `accept-base` = `accept-fix`, деливерабл — сам тест; эквивалент доказан инъекцией и повтором ошибки.
- Якорь SOP `accept-base~1` (d3d7638) даёт `5 passed`, что не совпадает с `## Текущий вывод`; карточка не врёт — её запись воспроизводится на `dc9d271`, якорь устарел из-за перестановки тега.
- Исторический замер «21 файл в CRLF» невоспроизводим: состояние до нормализации не закоммичено.
- Linux и `core.autocrlf=false`/`input`; ветка `UnicodeDecodeError` не исполнялась; полный `pytest` прогнан один раз.

ЗАМЕЧАНИЯ:
1. Две строки `ПРАВКА` (бюджет 80 → 220, нормализация карточки) отвечены их же автором — лидом. Не блокирует: обе претензии воспроизведены приёмкой независимо, строк без ответа нет.
2. `## Что меняем` говорит «сейчас на диске 21 файл в CRLF», хотя на диске 0: формулировка описывает дефект до правки и после неё устарела.
3. `accept-base` содержит тест, поэтому `accept-base..accept-fix` пуст и проверка бюджета по этому якорю вакуумна; бюджет сверен по фактическому артефакту.

## Действие лида

Принято. Первый отказ был по делу: карточка ушла в коммит в CRLF, потому что `Path.write_text` на Windows переводит `\n` в `\r\n` — тест поймал ровно это, то есть работает.

Замечание 1 закрыто в протоколе, а не отговоркой: `ПРАВКА` от Keel — это уже принятое решение, а не запрос, и отдельного ответа не требует; ответ нужен на `ПРАВКА` от других ролей. Иначе лид не может внести собственную правку, не выглядя самоподтверждающим.

Замечание 2 принято как известное: карточка описывает состояние до правки, и это её смысл.
