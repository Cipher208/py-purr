# Карточка задачи
## Задача
Переводы строк в рабочем дереве не расходятся с git, и расхождение ловится тестом, а не обнаруживается на четвёртый раз вручную.
## Что меняем
`tests/test_line_endings.py` — новый тест: читает файлы, отслеживаемые git, и падает со списком, если в текстовом файле есть CRLF при объявленном `*.py text eol=lf` в `.gitattributes`. Плюс нормализация рабочего дерева: сейчас на диске **21** файл в CRLF, тогда как в git они лежат в LF — 7 `.py` (`purr/store.py`, `tools/crash_harness.py`, `tests/test_store.py`, `tests/test_event_bus.py` и три судьи в `.dev-team/`) и 14 `.md` (`CHANGELOG.md`, `README.md`, ADR и 11 в `.dev-team/archive/`). Первая редакция карточки говорила «7» — это была ошибка замера: я считал только `*.py`, а `.gitattributes` пинит `eol=lf` и для `*.md`. Репозиторий при этом консистентен — расходятся именно рабочие копии, поэтому `git status` чист и проблема невидима. Цена уже заплачена: строковые замены по `\n` в этих файлах трижды молча не срабатывали, а я трижды этого не замечал. Продукт не меняется: правка только в тестах и в рабочем дереве.

## Команда прогона

## Критерий приёмки
Команда возвращает `0` и печатает `passed`. Обе стороны обязательны: сейчас тест обязан **падать** со списком CRLF-файлов (красное — до нормализации), а после нормализации проходить. Третья сторона: если снова создать `.py` с CRLF и добавить его в git, тест обязан снова упасть и назвать этот файл — иначе он декоративный. Отдельно: тест не должен падать на бинарных файлах (`.png`, `.db`) и на файлах вне git.

## Отчёт
**Сделано.** Добавлен `tests/test_line_endings.py`: он читает файлы, отслеживаемые git, и падает со списком, если в текстовом файле есть CRLF при объявленном `eol=lf`. Рабочее дерево нормализовано — 21 файл (7 `.py` и 14 `.md`) переписан из индекса в LF. Поведение продукта не менялось: правка только в тестах и в байтах рабочего дерева. Коммиты `d3d7638` (тест), `6b5aed4` (форматирование теста), документация — waiver. Артефакт 196 строк при бюджете 220.

**Чем доказано.** Вердикт `ПРИНЯТО` — `.dev-team/verdict/verdict-015.md`, приёмщик Warder, 13 проверок, второй заход. Ключевое:
- байтовая перепись 100 отслеживаемых файлов: 0 CRLF, включая `.dev-team/`; `git ls-files --eol` → 0 строк `w/crlf`;
- тест не вакуумный: внедрённый `crlf_probe.py` → `exit=1` с именем файла и числом строк; снятие → `exit=0`;
- **повтор моей собственной ошибки пойман:** `Path.write_text` на `card.md` даёт 35 CRLF → `exit=1` с именем файла;
- скоуп не фиктивный: `.png` с CRLF, `.gitattributes`/`.gitignore`/`LICENSE` в CRLF не ловятся, `README.md` в CRLF — ловится;
- CI: `ruff check` 0, `ruff format --check` 0, `pytest -q` 207 passed.

**Что осталось непроверенным.** Классический откат по тегам невозможен: `accept-base` = `accept-fix`, деливерабл — сам тест; эквивалент доказан инъекцией. Исторический замер «21 файл» невоспроизводим — состояние до нормализации не закоммичено. Linux и `core.autocrlf=false` не проверялись: всё на Windows с `autocrlf=true`.

**Два отказа, оба по делу.** Первый: карточка ушла в коммит в CRLF, потому что `Path.write_text` на Windows переводит `\n` в `\r\n`. Тест поймал ровно это — то есть он работает с первого дня. Второй причиной был бюджет: гейт видел 4 строки форматирования, а артефакт — 196; поднял до 220 замером.

**Что это меняет в работе.** Писать текстовые файлы в этом репозитории нужно байтами, а не `write_text`: иначе файл молча становится CRLF и гейт краснеет. Правило записано, потому что ошибка воспроизводимая, а не разовая.

**Пункт из очереди оказался устаревшим.** `uv.lock` не устарел: в нём `ruff 0.17.2`, совпадает с пином, и он намеренно в `.gitignore` (строка 42), поэтому в клон не приезжает и CI его не читает. Действий не требует.
