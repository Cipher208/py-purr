# ADR-001 — Контракт доставки события в журнал

**Дата:** 2026-10-30 (редакция 2: выбор владельца сменился с A на C)
**Автор:** Vitruv (system-architect)
**Карточка:** `.dev-team/card.md` (дефект, тип правки «поведение», бюджет 220)
**Статус:** владелец выбрал вариант **C** — журнал в той же БД и той же транзакции. Варианты A и B оставлены ниже как отвергнутые, с ценой и причиной отказа. Поле `## Решение` пустое: его заполняет Keel словами владельца.

## Контекст

### Что доказано стендом (на этой машине: Windows, Python 3.11.14, SQLite 3.50.4, WAL)

Команда карточки на текущем коде:

```
PYTHONPATH=. .venv/Scripts/python.exe tools/crash_harness.py run-journal-txn 1
run 1: маркер сброса=да | tx в KV 500/500 | событий tx 3 | разрыв 497 | integrity ok / журнал ok
EXIT=1
```

Что за этим стоит (`HARNESS-RESULTS.md`, строки 88-104):

1. Подтверждённая запись переживает убийство процесса: **954 из 954**.
2. Открытая транзакция не оставляет половины: **0 из 500** в шести прогонах.
3. Журнал может отставать от KV: на одиночной записи — **ровно на одно событие** (3 из 12 прогонов; 4 из 4 при расширенном окне), на транзакции — **497 из 500** в трёх прогонах из трёх.
4. **Фантомов не бывает ни разу**: 0 в 12 + 4 + 3 прогонах. Причина видна по коду — событие пишется после коммита: `store.py:223-228` (`self._commit()`, затем `self._journal_emit(...)`).
5. Размер разрыва ограничен только размером пачки: механизма восстановления потерянных событий нет, после рестарта ничто о дыре не сигналит.

### Замер, который и определил смену выбора владельца

При аварийном убийстве **никакое исключение не бросается**. Проба (`probe_kill.py`, штатный режим стенда `write-journal-txn`):

```
BATCH_START получен: True
маркер сброса поставлен: True
stderr ребёнка пуст: True
в stderr есть JournalFlushError: False
длина stderr: 0
```

Ноль байт в stderr — процесса уже нет, `JournalFlushError` (`store.py:24-30`, `store.py:89-94`) поднимать некому. Отсюда:

- **повтор** лечит только те отказы, при которых процесс жив: чужая блокировка журнала, краткий I/O, диск полон на секунду. В сценарии стенда он не срабатывает ни разу;
- **маркер** фиксирует потерю, но не устраняет её. «Разрыв 0» вариант A не даёт никогда;
- значит цена A — треть на одиночной записи, до 16.39 с в худшем случае и вторая таблица — платится за то, чтобы потеря была **видимой**, а не за то, чтобы её не было.

Владелец, увидев это, выбрал вариант C: атомарность по построению вместо фиксации потери.

### Что не доказано

- **Мультипроцесс, Linux, сбой диска, долгая нагрузка** — не проверялись (`HARNESS-RESULTS.md:132`). Прод на VPS — Linux. Все замеры ниже — Windows.
- **Повтор записи события не проверялся ни разу** (относится к отвергнутому A): стенд не умеет инжектить отказ `append` при живом процессе, он умеет только убивать процесс.

### Границы задачи (из карточки)

Файлы: `purr/store.py`, `purr/event_stream.py`, `tools/crash_harness.py`, `CHANGELOG.md`. Бюджет 220 строк. Критерий приёмки: `run-journal-txn` возвращает `exit=0`, и при этом либо `разрыв 0`, либо **отдельный процесс, запущенный ПОСЛЕ аварии, читает явный маркер потери с числом потерянных событий**.

Два следствия, которые видны по коду:

- `purr/state_machine.py:75-79` тоже пишет в журнал (`self._journal.append(Event(type=EventType.STATE, topic="fsm", ...))`), но через **свой** `db_path`, а не через `Store`, и **не входит в границы**. Там разрыв останется (замер и разбор — раздел C.1).
- `purr/__init__.py` в границы не входит. Если из публичного API что-то удаляется (`JournalFlushError` — раздел C.3), это правка карточки или явное решение оставить мёртвый экспорт.

## Решение владельца

Дословно (Лили, 2026-10-30), после показа замеров по A:

> «Тогда вариант C»

Предыдущая формулировка, от которой владелец отказался (Лили, 2026-10-29):

> «Давай подумаем, может можно повтор делать, если событие не прошло плюс ставить маркер»

Что следует технически из «варианта C» — это расшифровка, а не мой выбор:

1. **Таблица `events` переезжает в файл данных.** Разрыва нет по построению: событие и запись KV либо оба в коммите, либо оба отсутствуют.
2. **Маркер не нужен.** Незачем фиксировать потерю, которой не бывает; `journal_gaps()`/`acknowledge_journal_gaps()` из первой редакции этого ADR не появляются.
3. **Повтор не нужен.** `journal_attempts`, `DuplicateEventError`, `correlation_id` как метка набора — тоже не появляются.
4. **Меняется класс отказа.** Сбой записи события теперь откатывает данные (замер M7, раздел C.4), а не оставляет их durable. Это осознанная смена смысла, а не побочный эффект.
5. **Журнал перестаёт быть отдельным файлом.** Независимая подрезка/выгрузка/бэкап журнала без блокировки данных — невозможны. Это цена, а не деталь.

## Варианты

### Вариант 0 — ничего не делать (база для сравнения, карточку не закрывает)

**Что делает:** оставляет `commit → append` как есть (`store.py:223-228`, `store.py:400-405`).

**Цена:** 0 строк кода, 0 тестов, 0 мс. Разрыв остаётся: `497 из 500`, `exit=1` — замер выше, воспроизводится каждым прогоном.

**Что это значит по-человечески:** «Мы знаем, что при аварии часть истории пропадает молча, и продолжаем с этим жить».

**Что станет невозможным:** критерий приёмки карточки недостижим по определению; `run-journal-txn` навсегда красный; любое расследование инцидента начинается с «а сколько событий не доехало — неизвестно».

**Критерий ошибочности:** вариант уже ошибочен — стенд отказывает, карточка открыта. Держать его можно только как явное «принято, живём так», записанное в README.

### A. Повтор + маркер — ОТВЕРГНУТ владельцем 2026-10-30

**Почему отвергнут (одной строкой):** платит треть на одиночной записи, до 16.39 с в худшем случае и вторую таблицу с миграцией `Store` v2→v3 — за то, чтобы потеря стала **видимой**; «разрыв 0» не даёт никогда, а при убийстве процесса повтор не срабатывает ни разу (0 байт stderr, замер выше). C даёт тот же ноль разрыва дешевле и без второй таблицы.

**Что делал бы:**
- `_journal_emit` и `_journal_flush` повторяют `append` при отказе; бюджет попыток ограничен; дубликат id трактуется как успех.
- Перед коммитом данных (в той же транзакции) пишется строка-маркер: `write_id`, `claimed`, `started_at`; события помечаются `correlation_id = write_id`.
- После успешного сброса маркер снимается одним `DELETE`+commit.
- Отдельный процесс читает незакрытые маркеры, считает по `correlation_id`, сколько событий доехало.

**Цена (измерено, temp-скрипты вне репозитория):**

| Что | Число | Чем измерено |
|---|---|---|
| Повтор в штатном пути, когда сбоев нет | лишних SQL — 0; дельта в пределах дрейфа машины (A/A −11.7%, A/B +12.8%) | `aa.py` |
| Дубликат id как успех: цена пути исключения | 0.019 мс (против 0.005 мс у предварительного `SELECT` по id — в 3.7× дороже, но только на повторе) | `bench.py` 5a/5b |
| Маркер: строка внутри транзакции данных | +0 мс (в шуме: −1.9%…+5.4% на пачке 5000) | `bench6.py` 2a/2b, `bench3.py` 10a/10b |
| Маркер: снятие (один `DELETE`+commit на запись) | +0.062…+0.080 мс на одиночный `set()` (+26…35% к пути с журналом 0.228 мс) | `bench6.py` 1a/1b, `bench2.py` 7b/7c |
| Маркер на пачку | ≤ 0.1 мс на транзакцию (один commit) | `bench3.py` 10 |
| Чтение маркера новым процессом | 0.005…0.007 мс (строка), 0.006 мс (подсчёт по `correlation_id` при 500 и при 100 000 событиях) | `bench3.py` 8b/8c/8d |
| Миграция схемы (новая таблица) | 13.51 мс на первом открытии, 5.37 мс на последующих | `bench4.py` M |
| Отказ журнала при живом процессе: `set()` | `sqlite3.OperationalError` через 5.44 с, **данные в KV уже записаны** | `bench5.py` 1 |
| То же внутри `transaction()` | `JournalFlushError` через 5.45 с, данные записаны | `bench5.py` 2 |
| Бюджет 3 попытки при живой блокировке | 16.39 с на одну запись | `bench5.py` 3 |
| Маркер переживает убийство, читается новым процессом | `{"marker": true, "claimed_events": 500, "events_in_journal": 3, "missing": 497, "tx_in_kv": 500}`; чистый прогон — `{"marker": false, "tx_in_kv": 500}` | `proto.py` |

**Что это значит по-человечески:** «Каждая запись станет чуть дороже — одиночная примерно на треть, пачка почти незаметно; зато после сбоя отдельная программа сможет сказать: вот тогда потерялось ровно столько-то событий».

**Что ломало бы:** вторая таблица `_purr_journal_gap` в файле данных; смена типа исключения на одиночном пути; маркер **не восстанавливает** события, только фиксирует потерю; в окне между коммитом данных и сбросом журнала (50–286 мс на пачку 500) маркер виден читателю как «идёт запись», и читатель обязан отличать это от потери.

**Критерий ошибочности A (записан, хотя A отвергнут — он объясняет, что именно проверять у C):**
1. `run-journal-txn` даёт `разрыв > 0` при читаемом маркере с `missing = 0` — маркер врёт.
2. В проде найден ключ в KV без события, о котором `journal_gaps()` молчит.
3. `journal_gaps()` непуст после чистых остановок чаще 1 раза на 1000 записей — маркер шумит.
4. Одиночная запись дороже 0.31 мс, пачка 5000 дороже 1048 мс.
5. Отказ журнала у `set()` выходит как `sqlite3.OperationalError` — повтор не дошёл до одиночного пути.

### B. Намерение до коммита (intent/complete вокруг коммита) — ОТВЕРГНУТ

**Почему отвергнут:** +46% на одиночной записи (0.3346 мс против 0.2288 мс у A, замер `bench7.py`), и **точного числа потерянных событий не даёт** — на момент записи намерения событий ещё не существовало, ответ всегда «от 0 до размера пачки». Плюс меняет класс отказа: мёртвый файл журнала делает невозможной любую запись в KV.

**Цена (измерено):**

| Что | Число | Чем измерено |
|---|---|---|
| Одиночный `set()` (4 commit вместо 2) | 0.3346 мс против 0.2288 мс у A: **+0.106 мс, +46%** | `bench7.py` |
| `mset` 5000 (2 лишних commit на 5000 append) | 1029.71 мс против 998–1060 мс у A — **в шуме, цена не измеряется** | `bench4.py` B |
| Миграция схемы | та же новая таблица: 13.51 мс первое открытие | `bench4.py` M |

**Что это значит по-человечески:** «Каждая запись станет дороже почти в полтора раза, а после сбоя система сможет сказать только “возможно, что-то потерялось”, но не “сколько”».

**Что ломает / что станет невозможным:** точное число потерянных событий недостижимо; ложные тревоги (процесс убит между намерением и коммитом данных — данных нет, потери нет, а маркер есть); порядок записи переворачивается, и отказ журнала начинает блокировать запись данных.

**Критерий ошибочности:** доля незакрытых намерений после чистых остановок выше 1 на 1000 записей; хотя бы один инцидент, где по маркеру «возможно, дыра» ручная сверка дала 0 потерь; `set()` при недоступном журнале перестал проходить.

### C. Журнал в той же БД и той же транзакции — ВЫБРАН ВЛАДЕЛЬЦЕМ

**Что делает:** таблица `events` живёт в файле данных; вставка события становится частью транзакции `set()`/`mset`/`incr`/`delete`/`expire`. Атомарность полная: либо данные и события, либо ничего. Разрыва нет по построению, маркер и повтор не нужны.

**Цена на одиночной записи (измерено, `m1c_branches.py`, один прогон, одни и те же ключи):**

| Что | Число |
|---|---|
| `set()` создаёт ключ: A → C | 0.1695 → **0.1192 мс** (−0.0503, −29.7%) |
| `set()` перезаписывает ключ: A → C | 0.1312 → **0.1165 мс** (−0.0147, −11.2%) |
| Цена строки события в **отдельном** файле (A − KV без журнала) | +0.1316 мс (создание) / +0.0854 мс (перезапись) |
| Цена строки события **в той же транзакции** (C − KV без журнала) | **+0.0814 мс** (создание) / **+0.0708 мс** (перезапись) |
| Из них обслуживание 4 индексов `events` | +0.0142 / +0.0156 мс |

**Поправка к первой редакции этого ADR.** Там стояло «C = 0.1126 мс/`set()`, −51%». Это число получено на прототипе `bench7.py`, где C оборачивал каждый `set()` в явный `transaction()` и вставлял 6-колоночную строку в таблицу `events` **без индексов**. На реальной схеме (9 колонок, 4 индекса) экономия не −51%, а **−30% при создании и −11% при перезаписи**. Проверено прямо: в `m1c` тот же C с удалёнными индексами даёт 0.1050 мс, с индексами — 0.1192 мс, то есть 0.0142 мс и есть цена четырёх индексов `events`. `bench7.py` воспроизводится и сегодня (A 0.2419, C 0.1094), но его проценты относятся к прототипу с урезанной схемой, а не к продукту.

**Цена на пачке (измерено, `m1b_real.py`, 3 прогона):**

| Что | Число |
|---|---|
| `mset` 5000 без журнала | 31.49 мс |
| `mset` 5000, журнал в отдельном файле (A) | 1008.22 мс |
| `mset` 5000 + 5000 событий в одной транзакции (C) | **177.45 мс** (5.7× дешевле A) |

Первая редакция давала для C 108.91 мс (`bench4.py`) — там события вставлялись `executemany` в таблицу без индексов и с урезанной строкой. 177.45 — та же операция на реальной схеме через настоящий `EventStream._insert`.

**О сравнимости чисел.** Абсолюты `set()` в разных прогонах расходятся сильнее, чем допускает дрейф машины: A в `m1c` (перезапись) — 0.1312 мс, A в `bench7.py` (перезапись, тот же реальный код) — 0.2419 мс, то есть 84%. Причину не нашёл; поэтому **сравнивать можно только внутри одного прогона**, и все выводы этого ADR построены на внутрипрогонных разностях (A−KV, C−KV, C−A в одном скрипте). Числа A в таблицах вариантов A и B — из `bench6`/`bench7`; числа A в таблице C — из `m1c` того же прогона, что и C. Смешивать их в одном отношении нельзя.

**Что именно мерилось в прототипах.** Тело `set()` взято из `store.py:191-229` с двумя правками: emit поднят выше `_commit()`, ветка `ttl` опущена (её не использует ни один замер, а в A и в C она добавляет один и тот же statement). Всё остальное — настоящий `Store`, настоящий `EventStream._insert`, реальная схема с четырьмя индексами.

**Что это значит по-человечески:** «Потери истории не будет вообще — либо запись и её событие сохранены вместе, либо не сохранены вместе. Пачка записей станет в пять раз быстрее, одиночная — процентов на десять-тридцать. Взамен журнал перестанет быть отдельным файлом, и пока одна часть программы пишет большой блок данных, другая не сможет дописать событие — будет ждать».

**Что ломает / что станет невозможным** — детально в разделе «Устройство C»: отдельный файл журнала, независимая подрезка/выгрузка/бэкап, `JournalFlushError` как класс отказа, двухфайловый режим `Store(..., journal=EventStream("events.db"))`.

**Критерий ошибочности C** — раздел «Критерий ошибочности C» ниже.

## Устройство C (то, чего для C не хватало)

### C.1 Судьба двухфайлового режима

Сегодня `Store(path, journal=EventStream(other_path))` — два файла, и разрыв возникает именно там. Под C режим один. Три кандидата, цена каждого измерена или посчитана по коду:

| Кандидат | Цена | Последствия |
|---|---|---|
| **C.1-a: `EventStream` принимает путь и молча игнорирует его** | 7 тестов падают всё равно (они читают `j.db`, который останется пустым), плюс `EventStream("events.db")` пишет не туда, куда просили | Ложь в API: один и тот же объект означает разные файлы в зависимости от того, кто его держит. Оператор не узнает, что журнал переехал, — старый файл просто перестанет пополняться |
| **C.1-b: чужой путь отвергается явной ошибкой в `Store.__init__`** | 7 тестов правятся (4 только путь, 3 меняют смысл), 2 вызова в стенде переписываются (стенд в границах карточки), 1 Breaking в CHANGELOG | Публичный вызов `Store(db, journal=EventStream("events.db"))` начинает падать `ValueError` на старте. Явно и сразу, а не молчаливым разрывом. `EventStream("events.db")` сам по себе (README:146) не затронут |
| **C.1-c: два режима — co-located (атомарно) и раздельный (с прежним разрывом)** | 0 тестов, 0 Breaking, но остаются ~50 строк журнальной обвязки (`store.py:24-30`, `53-58`, `60-67`, `69-94`, вызовы в `transaction()`) и 5 точек emit с ветвлением | Дефект карточки остаётся достижим через публичный API в одном из двух режимов, и ничто не говорит оператору, в каком режиме он работает. Стенд обязан держать два сценария вместо одного |

**Выбран C.1-b.** Основание: C.1-c оставляет ровно тот дефект, ради которого открыта карточка, и требует держать два контракта (буфер + `JournalFlushError` против «в транзакции») в одном классе; C.1-a не даёт ничего, кроме экономии правок, и врёт при этом в API. C.1-b — единственный вариант, где у продукта один журнальный контракт, и нарушение видно сразу на старте.

**Что это значит по-человечески:** «Если программа настроена держать историю в отдельном файле, она теперь при запуске скажет об этом прямо и остановится, вместо того чтобы тихо терять часть истории».

**Последствия для тех, кто уже использует `journal=`, одной фразой:** при старте они получат `ValueError` с указанием, что журнал теперь живёт в файле данных, вместо тихого продолжения работы с разрывом.

**Что с `purr/state_machine.py:75-79`.** Он пишет в журнал **мимо `Store`**: `self._journal.append(...)` на своём `EventStream`, у которого свой `db_path` (`state_machine.py:59-79`), и порядок там `_save_state()` (commit, строка 299) → `_journal_emit` (строки 164-171). Под C.1-b `StateMachine` не меняется вообще: его тесты (2) остаются зелёными, и **разрыв для событий `topic="fsm"` остаётся ровно тем же**, что сегодня. Это надо назвать вслух: контракт C покрывает `Store`, а не весь продукт. Закрыть FSM-дыру — правка карточки (добавить `purr/state_machine.py` в файлы) и второй цикл; в текущих границах её закрыть нельзя, не выйдя за бюджет.

### C.2 Схема, реестр, миграция

**Чей реестр.** `_purr_schema` — реестр **на движок**, а не на файл (`backend.py:32-45`), и это ровно тот случай, ради которого он так сделан. Измерено (`m3_schema.py`, оба порядка открытия):

```
Store→EventStream: реестр [('event_stream', 2), ('store', 2)], user_version=2
EventStream→Store: реестр [('event_stream', 2), ('store', 2)], user_version=2
таблицы: ['_purr_schema', 'cursors', 'events', 'kv', 'kv_meta']
```

Оба движка создают свои таблицы в одном файле, конфликта нет, `no such table` не возникает ни в одном порядке.

**Чей `user_version`.** Один счётчик на файл, и он общий. Сегодня оба движка на версии 2, поэтому счётчик совпадает с обеими записями реестра. Проверено, что расхождение не ломает ничего (`m4_read.py`): после того как в файл зашёл движок с `SCHEMA_VERSION=3`, `user_version` стал 3, строка `store` в реестре осталась 2, и `Store` после этого открывается и пишет. Источник истины — реестр; `user_version` только догоняет максимум.

**Кто гоняет миграции журнала.** `Store` обязан убедиться, что таблицы `events`/`cursors` есть в его файле: `journal.run_migrations()` (или внутренний `EventStream` на своём пути) в `__init__`. Цена: 14.1 мс на втором движке, 16.1 мс на существующем файле с данными (10.5 МБ KV, 50 000 ключей) — измерено, данные целы, размер файла не изменился.

**Миграция существующей БД, где журнал лежал отдельно.** Схема мигрируется на месте, данные переносить **не обязательно**: старый `events.db` остаётся валидным самостоятельным `EventStream` (измерено: открывается, 100 000 событий на месте, файл не тронут, 30.5 МБ). Цена переноса, если он понадобится: `ATTACH` + `INSERT..SELECT` 100 000 событий — **958 мс**, файл данных вырастает с 10.5 МБ до 41.1 МБ.

**Цена отказа от переноса, и она не нулевая:** новый журнал начинается пустым, а консьюмер, который резюмирует по курсору, прочитает пустой лог и решит, что событий не было. Значит при переключении курсоры надо сбросить (`reset_cursor`) или явно указать консьюмеру на архивный файл. Это запись в CHANGELOG и в README, а не деталь реализации.

### C.3 Транзакция

**Буфер исчезает.** `_journal_buffer` (`store.py:53-58`) существует только потому, что событие нельзя было писать внутри транзакции. Под C событие пишется сразу, в тот же коннект. Вместе с буфером уходят: per-thread ветка в `_journal_emit` (`store.py:64-66`), `_journal_flush` (`store.py:69-94`), `self._journal_buffer.clear()` в `transaction()` (`store.py:137`) и `self._journal_flush()` (`store.py:141`). Построчно: `store.py:24-30` — 7 строк, `53-58` — 6, `60-67` — 8, `69-94` — 26, плюс 2 строки в `transaction()`; всего **49 из 480** строк файла. Из них `_journal_emit` не исчезает, а меняет тело: остаётся ~6 строк вместо 8.

**`JournalFlushError` теряет производителя.** Класс (`store.py:24-30`, экспорт `__init__.py:33,41`) означает «данные durable, журнал нет». Под C такого состояния не существует: сбой вставки события откатывает транзакцию целиком (замер M7 ниже). Класс становится мёртвым кодом. Решение о его судьбе — правка карточки: либо удалить вместе с экспортом (Breaking для тех, кто его ловит), либо оставить с deprecation-докстрокой. Мой замер говорит, что **поймать его больше нельзя ни при каком сценарии** — то есть оставленный класс будет ловить пустоту.

**Порядок операций.** Emit переезжает **выше** `_commit()` во всех пяти точках: `set` (`store.py:228`), `delete` (`store.py:263`), `expire` (`store.py:311`), `incr` (`store.py:370`), `mset` (`store.py:404-405`). Детали, которые надо не потерять:
- `delete` эмитит только при `cur.rowcount > 0` (`store.py:261-263`) — `rowcount` читается до коммита, порядок сохраняется;
- `incr` коммитит сам (`store.py:364-365`), emit идёт перед этим коммитом; внутри `transaction()` коммита нет вообще, и событие просто остаётся в транзакции вызывающего;
- `mset` сейчас собирает payload'ы в список и эмитит после коммита (`store.py:387-405`); под C вставка идёт в том же цикле — либо построчно, либо `executemany` перед коммитом. Замеренная цена построчного пути — 177.45 мс на 5000 против 31.49 мс без журнала;
- `append_many` под C не используется: `Store` и раньше звал `append` по одному событию. Замер для справки: `append_many` 5000 = 147.05 мс против 998–1060 мс поштучно (`bench4.py` C2, первая редакция).

**Что видит `read()` внутри открытой транзакции (измерено, `m4_read.py`).** Внутри `transaction()` после двух `set()`:

```
свой коннект Store видит событий 3   (включая незакоммиченные)
отдельный EventStream видит событий 1 (только закоммиченное)
свежий коннект снаружи видит {'events': 1, 'kv': 1}
после commit снаружи:              {'events': 3, 'kv': 3}
read() снаружи во время транзакции: 0.012 мс/вызов (не блокируется)
```

Три следствия:
1. Событие и запись становятся видимыми **одновременно** — снаружи ни разу не видно 3 события при 1 ключе.
2. Консьюмер обязан читать **своим** `EventStream` (свой коннект). Если он читает коннектом `Store`, он увидит незакоммиченное — то есть `read()` внутри транзакции честно показывает грязные данные, и это не то, что нужно консьюмеру.
3. `es.read()` на переданном инстансе не блокируется открытой транзакцией (WAL), значит «журнал в той же БД» не мешает читателям.

**Валидация и дубликаты.** `Store` перестаёт звать `EventStream.append`, а значит перестаёт получать `_validate_timestamp` и `ValueError("duplicate event id")`. Id генерирует `Store`; коллизия uuid4 практически невозможна, но её следствие под C тяжелее: `IntegrityError` откатит всю запись, а не только событие. Это риск на одну строку, и его место — комментарий в коде, а не открытие в этом ADR.

### C.4 Цена C

**Одиночная запись и пачка** — таблицы в разделе «Вариант C» выше. Главное: строка события в той же транзакции стоит **+0.081 мс** (создание) / **+0.071 мс** (перезапись), то есть примерно столько же, сколько в отдельном файле (+0.132 / +0.085). C экономит не на строке события, а на **втором коммите**.

**Конкурентность — главная цена C, и вот её число.**

Общий файл значит общий write-lock: пока одна сторона держит транзакцию записи, другая не может писать. Измерено (`m2b_conc.py`, два процесса, `busy_timeout=5000`):

| Сценарий | Общий файл (C) | Два файла (A) |
|---|---|---|
| Независимый писатель журнала, пока кто-то держит `BEGIN IMMEDIATE` 1000 мс | первый `append` ждёт **1067.9 мс** | **0.4 мс** |
| То же, но блокировку держит настоящая транзакция `mset` 5000 (37.3 мс) | `append` ждёт **44.7 мс** | **0.4 мс** |
| `set()` при чужой блокировке записи 6 с | падает через **5477 мс**, `database is locked`, **ключа в базе НЕТ** | падает через **5470 мс**, `database is locked`, **ключ в базе ЕСТЬ** |
| Подрезка журнала: `DELETE` 99 900 событий из 100 000 | **633.1 мс** удержания write-lock файла данных | 551.8 мс, но lock только на файле журнала |
| `set()` при параллельном писателе журнала (5314 append'ов за окно) | медиана 0.050 мс, **p95 0.09 мс**, max 54.0 | медиана 0.169 мс, p95 0.59 мс, max 77.7 |
| Два писателя, 2 с: KV-записей + append'ов | **12 308 + 5 551** | 3 798 + 4 720 |

Читать это надо так: **общий lock наказывает не за каждую операцию, а за длинную.** Короткие чужие записи почти не мешают (p95 0.09 мс), потому что каждая держит lock микросекунды. Но любая длинная транзакция на одной стороне останавливает другую на **всю свою длительность**: 44.7 мс за `mset` 5000, до 633 мс за подрезку журнала, до 5477 мс (и отказ) за чужую блокировку. При A эти вещи блокировались независимо.

**Сбой журнала теперь откатывает данные (измерено, `m7_rollback.py`):**

| Сценарий | Что осталось в базе |
|---|---|
| C: `set("bad")` вне транзакции, вставка события падает | `OperationalError`, ключа `bad` нет, события нет. Ключ `good` на месте |
| C: то же внутри `transaction()` с тремя ключами | откатились **все три** ключа и все события |
| A: тот же сбой | `JournalFlushError`, в базе **все три** ключа — данные durable, журнал нет |

Это и есть смена класса отказа, названная в разделе «Решение владельца» пунктом 4: «журнал — вторичный артефакт» больше не верно.

### C.5 Чем доказано, что C закрывает критерий карточки

Прототип `m5_crash.py`: настоящий `Store` с подклассом, у которого emit стоит до коммита (тело `set()` скопировано дословно из `store.py:191-229`, изменена одна строка порядка), один файл, сценарий стенда — 20 подтверждённых ключей, затем транзакция из 500 записей с событиями, убийство процесса внутри транзакции.

```
убийство на PROGRESS 100, 3 прогона: tx в KV 0/500 | событий tx 0 | разрыв 0 | integrity ok
убийство на PROGRESS 450, 3 прогона: tx в KV 0/500 | событий tx 0 | разрыв 0 | integrity ok
чистый прогон без убийства:          tx в KV 500/500 | событий tx 500 | разрыв 0 | integrity ok
```

Шесть из шести убийств дают **разрыв 0** и ни одного частичного коммита; чистый прогон даёт 500/500 и 520 событий (20 до транзакции + 500 в ней). Критерий карточки «`exit=0` и `разрыв 0`» под C достижим, и второй ветки критерия (маркер) не требуется.

**Но:** критерий проверяется командой `run-journal-txn`, а стенд сегодня строит **два** файла (`crash_harness.py:397-431`, `419`: `store = Store(kv_path, journal=journal)` где журнал на `ev_path`). Под C.1-b этот вызов начнёт падать. Стенд обязан перейти на один файл — иначе приёмочная команда проверяет конфигурацию, которой в продукте больше нет. Это правка `tools/crash_harness.py` (в границах карточки), а не «побочная».

## Критерий ошибочности C

C надо откатывать, если наблюдается любое из:

1. **Разрыв появился.** В проде найден ключ в KV без события `topic="store"` о нём. По построению C это невозможно, значит атомарность нарушена — например, кто-то пишет в журнал мимо `Store` (как `state_machine.py`) и это принимают за покрытое контрактом.
2. **Общий lock стал узким местом.** Доля `set()`, ждущих дольше 100 мс, выше 1 на 1000 записей — то есть длинные транзакции или подрезка журнала случаются достаточно часто, чтобы общий write-lock определял отклик KV. База для сравнения измерена: p95 0.09 мс, когда чужие записи короткие; 44.7 мс за `mset` 5000; 633 мс за подрезку 100 000 событий. Одна подрезка на 1000 записей уже даёт эту долю — значит порог ловит именно частоту, а не сам факт.
3. **Сбой журнала останавливает запись.** Доля отказов KV-записи, вызванных именно журналом (а не данными), выше 1 на 10 000. Под C это прямая цена, и она должна оставаться исчезающе малой.
4. **Понадобилась независимая работа с журналом.** Подрезка, выгрузка наружу или отдельный бэкап журнала без блокировки данных — если это понадобилось, значит отдельный файл был нужен, и вариант себя не оправдал.
5. **Цена выше измеренной.** `set()` дороже 0.16 мс (создание) / 0.14 мс (перезапись); `mset` 5000 с событиями дороже 250 мс.
6. **Breaking сработал по живому.** Кто-то из пользователей получает `ValueError` про путь журнала или ловит `JournalFlushError`, которого больше нет, — значит переход надо было делать через режим совместимости, а не через отказ.

## Что не удалось измерить

- **Linux и `SIGKILL`** — все замеры на Windows (Python 3.11.14, SQLite 3.50.4). Прод на VPS — Linux; поведение `TerminateProcess` и `SIGKILL`, а также тайминги WAL различаются. Прогон `m5_crash.py` на Linux не делался.
- **Конкуренцию больше двух писателей** на общем файле: измерены два процесса. Как ведёт себя общий lock при 4–8 писателях — не проверял.
- **Реальный профиль прод-нагрузки**: какая доля времени приходится на длинные транзакции (`mset`, подрезка). Цена C целиком зависит от этой доли, и её я не измерял — измерены только длительности самих операций.
- **Интеграцию в код продукта**: я не правил `Store`. Измерен прототип-подкласс с дословно скопированным телом `set()` и одна изменённая строка порядка; влияние на 201 тест не прогонялось (тесты под C меняются — таблица выше).
- **Сбой диска / I/O-ошибку носителя**: инжектировалась только чужая блокировка и программный отказ вставки события, не отказ железа.
- **Поведение при исчерпании `busy_timeout` на вставке события внутри уже открытой транзакции**: замерен только отказ на первом же statement (5477 мс, ключ не записан). Сценарий «KV-строка вставлена, событие не влезло по таймауту» моделировался программным отказом (M7), а не реальным таймаутом.
- **Цену `_cleanup_orphans`/`_foreign_keys` при открытии общего файла с большой таблицей `events`**: `backend.py:192-215` обходит все FK на каждом новом коннекте; на 100k событий отдельно не мерил.

## Приложение A (отвергнуто вместе с вариантом A): как был устроен маркер

Оставлено как запись цены и как материал для будущего, если C окажется неверным по критерию 4 (понадобится независимая работа с журналом).

Маркер — строка в файле данных, в той же транзакции, что и запись: `_purr_journal_gap(write_id TEXT PRIMARY KEY, claimed INTEGER, started_at TEXT)`, `Store.SCHEMA_VERSION 2 → 3`, цена 13.51 мс на первом открытии. Публичный API: `journal_gaps() -> list[JournalGap]` с полями `write_id`, `claimed`, `missing`, `started_at`, `age_seconds`, и `acknowledge_journal_gaps() -> int`. Дубликат id трактовался как успех через `DuplicateEventError(ValueError)` — подкласс, чтобы три существующих теста (`tests/test_fixer_pass2.py:32,120,180`) остались зелёными (**гипотеза**: прогоном не проверялось).

Бюджет повторов A: 3 попытки по умолчанию, каждая ждёт `busy_timeout` 5000 мс, худший случай 16.39 с на одну запись, после исчерпания — `JournalFlushError` и маркер остаётся. Прототип `proto.py` показывал, что маркер переживает убийство и даёт точное число: `{"marker": true, "claimed_events": 500, "events_in_journal": 3, "missing": 497, "tx_in_kv": 500}`.

Почему это не понадобилось: под C потерять событие, не потеряв запись, невозможно (M5: 6 из 6 убийств — разрыв 0), а маркер фиксировал потерю, а не устранял её.

## Решение

**Выбор владельца (Лили, 2026-10-30): «Тогда вариант C».**

Обоснование одной строкой: co-located журнал убирает разрыв по построению, дешевле на одиночной записи (создание −29.7%, перезапись −11.2%) и в 5.7 раза дешевле на пачке из 5000, тогда как вариант A сохраняет разрыв и берёт +26…35% за маркер.

Принятая цена (см. `## Что ломается`): под длинной чужой блокировкой `set()` падает и ключа в базе не остаётся — при двух файлах ключ был бы записан; сбой вставки события откатывает данные транзакции. Это Breaking, попадает в CHANGELOG.
