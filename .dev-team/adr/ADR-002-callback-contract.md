### Почему колбэки оказались после коммита

Карточка предыдущей задачи (`.dev-team/archive/2026-11-05-fsm-rollback-sync.md:13`) требовала: «колбэки `on_exit`/`on_enter` не срабатывают для незафиксированного перехода». Перенести их после `conn.commit()` было единственным способом это обеспечить; `.dev-team/card.md:5` называет следствие прямо: «переход совершён полностью, а вызывающий видит ошибку и может повторить отправку». `verdict-020.md:30`: «Переход зафиксирован, а вызывающий получил исключение: классическая «тихая неправда» (P1)». CHANGELOG уже описал перенос, `CHANGELOG.md:138`: «**Callback contract changed:** `on_exit` now runs after a successful commit».

Исторический порядок до правки (команда `git show 2c64422^:purr/state_machine.py | sed -n '155,205p'`, **проверено**; ниже выписка с сокращениями):

```python
                if old_state.name in self._on_exit:
                    self._on_exit[old_state.name](old_state)

                new_state = State(...)
                self._current = new_state
                self._commit_state({...})

                if new_state.name in self._on_enter:
                    self._on_enter[new_state.name](new_state)
```

То есть до `2c64422` `on_exit` вызывался до коммита, `on_enter` — после; `self._current` публиковался до коммита. Отсюда два следствия, которые измерены в варианте 4.

## Находки

- **P1 🟠 «Тихая неправда» на базе — подтверждено.** `purr/state_machine.py:190-196`: `self._current = new_state` и колбэки идут после `_commit_state()`, внутри которого уже выполнен `conn.commit()` (`purr/state_machine.py:335`). Проба выше: вызывающий получает `ValueError`, состояние `B`, БД `('B', ...)`, событие `transition`, `on_enter` не вызван. Повторный `send('go')` → `False`. Соответствует `verdict-020.md:30`.
- **P1 🟠 Вариант 3 вносит новый путь той же природы — измерено.** Если компенсирующая запись сама падает, вызывающий получает `RuntimeError 'forced journal failure on compensation'`, а память и БД остаются `B/new` с событием `transition` и без компенсирующего события. Проба `probe_v3_fail.py` на клоне `v3-code`.
- **P1 🟠 Вариант 4 возвращает дефект verdict-020 — измерено.** При принудительном откате записи колбэки срабатывают для незафиксированного перехода: `calls == [('exit','A'),('enter','B')]` (оба до коммита) либо `calls == [('exit','A')]` (исторический порядок). `1` из `12` rollback-тестов красный. В историческом порядке исключение из `on_enter` по-прежнему приходит **после** коммита: память/БД `B/new`, события `['set','transition']` — P1 для `on_enter` не закрыт.
- **P3 🟢 Документационный разрыв.** README: `0` упоминаний `on_exit`/`on_enter`/`callback` при `6` разделах `###` и `24` маркерах кода (12 блоков); CHANGELOG: `4` строки о колбэках, все в `### Fixed` (строки 128-141). Изменение контракта в README не отражено вообще.

### Вариант 1 — изолировать исключения колбэков

**Что делает.** Каждый колбэк оборачивается в свой `try/except Exception`; исключение складывается в новый канал `StateMachine.callback_errors`, `send()` возвращает `True`. Ошибка записи из `_commit_state()` по-прежнему пробрасывается — она происходит до колбэков и в обёртку не попадает.

| Строк в тестах | `+70` | `70  0  tests/test_state_machine.py` |
| Существующих тестов, которые надо править | `0` | `219 passed` на клоне с правкой → `225 passed` с новыми тестами |
| Мест в CHANGELOG | `2` блока из `6` (`### Breaking`, `### Changed`/`### Fixed`) | `awk` по CHANGELOG |

| Правок карточки | `1` строка `ПРАВКА:` (`README.md` в границы) | `## Файлы в границах` = 4 файла |
| Диф (код + тесты) | `86` строк из `120` | `+84 -2` |

**Что это значит по-человечески:** Ошибка в дополнительном действии больше не мешает переключению: переключение считается успешным, а сама ошибка тихо складывается в отдельный список.

**Последствия.** Измерено пробой `probe_behavior.py` на `v1-code`: S1 `returned True`, `calls == [('exit','A'),('enter','B')]`, память/БД `B/new`, события `['set','transition']`; S2 (упал `on_enter`) тоже `returned True` с обоими колбэками; S3 `raised RuntimeError`, `calls == []`, состояние `A/old`; S4 без изменений. Появляется второе изменение контракта помимо подавления: `on_enter` теперь выполняется даже когда `on_exit` упал — на базе он не выполнялся (`calls == [('exit','A')]`). Канал `callback_errors` не очищается (`0` методов очистки), то есть список растёт всё время жизни машины. Исключение колбэка больше не прерывает `send()`: внешний код, использовавший его как сигнал «откатить свою работу», сигнал не получит. Повторный `send('go')` после ошибки по-прежнему `False`.

**Что станет невозможным.** Узнать об ошибке колбэка через исключение; остановить `send()` ошибкой колбэка; гарантировать, что `on_enter` не выполнится после падения `on_exit`; ограничить рост списка ошибок без нового API; поймать `BaseException` (`KeyboardInterrupt`, `SystemExit`) — обёртка ловит только `Exception` (**гипотеза**, не исполнялось).

**Сколько тестов ломается.** Существующих — `0` (`219 passed`). Новых на базе — `5` красных из `6`: `5 failed, 1 passed`. Формы падений измерены: `1` `AssertionError` на конкретном значении (`assert ('raised','ValueError','on_exit boom') == ('returned', True)`), `3` необработанных `ValueError`, `1` `AttributeError: 'StateMachine' object has no attribute 'callback_errors'` — последняя относится к запрещённой карточкой форме «not found». Значит при заморозке ассертов строкой `ПРАВКА:` тест-класс надо переписать так, чтобы красное было `AssertionError`, а не обращением к несуществующему атрибуту.

**Критерий ошибочности (через месяц):**
1. Ошибка колбэка ни разу не была прочитана из `callback_errors` — канал есть, потребителя нет; дефект стал невидимым, а не устранённым.
2. Список `callback_errors` вырос до размера, который влияет на память долгоживущего процесса, и понадобился метод очистки, которого в варианте нет.
3. Зафиксирован внешний вызывающий, который перестал получать исключение и молча пропустил реальный сбой в своём `on_exit`.
4. `on_enter`, выполненный после упавшего `on_exit`, произвёл побочный эффект, которого раньше не было (дублирование отправки/записи).

### Вариант 2 — явный сигнал о зафиксированном переходе
